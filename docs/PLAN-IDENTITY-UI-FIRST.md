# Plan: identity slice, UI first (with CLI sign-in)

Plan only, for provisio-mgr and Caleb. Nothing here is built, deployed or contacted. It implements the
first part of DESIGN phase 4 ("Provisio identity") and the sign-in half of phase 5 ("Publish"), with the
provenance UI as the first consumer and Scion after. Sources: `docs/DESIGN.md` (Identity, AT Proto storage
and publishing, Operations, Phased plan), `MIREN_PDS_PROOF.md` and its findings (linespec migration
dry-run repo), the provenance UI repo as it is today (`@clerk/react`, `api/clerk-repo-token.ts`,
`src/lib/platformClient.ts`, `platformMutationClient.ts`), and the CLI's `record.Store` interface.

Statements about third-party software (PDS settings, Bluesky behaviour, Miren features) are from memory
or from the proof, not re-checked. They are collected under "Assumptions to verify" and each is owned by a
milestone.

## 1. The slice

**Goal.** A person signs into the provenance UI with an AT Proto account, and the UI reads and writes their
provenance records through a Provisio record server instead of Clerk plus GitHub tokens. The same person
signs into the CLI with a device code, publishes a record, and sees it in the UI under the same account.

**Order of accounts.**

1. Bluesky handle (or any AT Proto account). No new identity infrastructure: the account lives on its own
   server and the auth service is the OAuth client.
2. Provisio handle (`name.provisio.social`). Needs the Provisio PDS.
3. GitHub and GitLab login. Later; not in this slice.

Bluesky first is deliberate: it lets sign-in, the record server, the UI and the CLI land before the PDS
and its certificate, backup and key-custody work, which are the long poles.

**In the slice**

- AT Proto OAuth sign-in in one Provisio auth service, one Provisio session (cookie for the UI, bearer
  token for the CLI and API).
- Device-authorization sign-in for the CLI, `PROVISIO_TOKEN` for CI.
- A record server that lists, reads and writes `dev.provisio.provenance.*` records in the signed-in
  user's AT Proto repo, with compare-and-swap writes.
- The UI reading and writing published records through it. `provenance publish`, `clone` and `import` in
  the CLI.
- The Provisio PDS on the Miren cluster, with backups and a restore drill, ready for the second sign-in.

**Out of the slice**

- Scion (it keeps Clerk until the UI is done), GitHub and GitLab login, the Jetstream indexer, search and
  backlinks across users, lineage records, Clerk user migration.
- **Private records.** Everything published to AT Proto is public (DESIGN, Privacy). The UI today also
  reads private repos with GitHub tokens. In this slice the GitHub-token path stays behind a flag for
  private repos, and the AT Proto path serves published (public) records only. See decision 7.

**What stays canonical.** Git is canonical for records that have a repo (DESIGN, "Moving away from git").
AT Proto holds the published copy. A UI edit to a published record becomes a new version record in the
user's repo, marked `origin: ui`, and `provenance import` brings it back into git as a new local version.
Details in section 4 and decision 6.

**Deployables.** Two Miren apps at first: `provisio-pds` (one fixed instance, a disk) and `provisio-api`
(auth and records in one process behind one route, split later if needed). The auth service needs a small
store for users, sessions, device codes and tokens: SQLite on a disk with the in-app backup that the proof
validated. Postgres arrives with the indexer, not before.

**Why TypeScript for the services.** The official AT Proto OAuth client (DPoP, PAR, client assertions) and
lexicon tooling are TypeScript libraries, DESIGN already assumes a TypeScript backend with a conformance
corpus against the Go hash code, and the UI is TypeScript. Writing OAuth by hand is the wrong place to save
effort. The sedum generators available today are Go ones (`cobra`, `go`), so the TypeScript services are
handwritten. They are still governed: one blueprint per service, imprints with the proof files as
`associated_specs`, tests as the proof. A TypeScript generator package is a separate decision for the sedum
owners; this plan does not depend on it.

**Why a confidential client in the auth service and not browser-only OAuth.** A browser-only client would
need no record server, but then the CLI, CI and (later) GitHub login have no shared session, sessions live
in each browser, and tokens are stored client-side. One confidential client keeps one session model and is
what DESIGN already decided.

## 3. The session model (UI, CLI, later Scion)

One Provisio session token for every client; its subject is the DID.

| Token | Lifetime | Carried as | Stored |
| --- | --- | --- | --- |
| Access token | 15 minutes, signed (public keys at the auth service's JWKS) | UI: `HttpOnly; Secure; SameSite=Lax` cookie on `.provisio.dev`. CLI and API: `Authorization: Bearer` | not stored by the server |
| Refresh token | 30 days, rotating (each use issues a new one, reuse revokes the family) | UI: second `HttpOnly` cookie scoped to the refresh path. CLI: credential store | hash only, in the auth DB |
| Personal token (CI) | until revoked or the expiry chosen at creation | `PROVISIO_TOKEN` environment variable | hash only; shown once |

- The record server and Scion verify access tokens against the JWKS; neither holds OAuth sessions.
- The AT Proto OAuth session (DPoP-bound, to the user's PDS) stays inside the auth service. The record
  server asks the auth service to act for a DID; it never sees PDS tokens.
- Personal tokens carry scopes: `records:read`, `records:write`, by project. A CI token cannot mint tokens.
- The UI cookie domain needs the UI on a `provisio.dev` host. It is on Vercel today (`vercel.json`);
  a custom domain there is enough. The UI never reads the cookie in JavaScript.

## 4. The CLI side

### Commands

| Command | Does |
| --- | --- |
| `provenance login` | Device flow against the auth service. Prints a verification URL and a short code, tries to open the browser unless `--no-browser`, polls until approved, expired or denied. Works over SSH and on machines with no browser. `--with-token` reads a personal token from stdin and stores it. |
| `provenance logout` | Revokes the refresh token at the server, deletes the local credential. If the server is unreachable it still deletes locally and says the server revocation failed. |
| `provenance whoami` | Prints handle, DID, where the credential came from (`env`, `keychain`, `file`), and when it expires. Exit status 1 when logged out. `--json` for scripts. |

Device flow follows RFC 8628: the CLI gets a device code and a user code, the user approves it in the
browser after signing in with AT Proto (the same sign-in as the UI), the CLI polls with the server's
interval and backs off on `slow_down`. The user code is short, from an alphabet without look-alike
characters, and expires in 10 minutes. The approval page names the CLI, the machine's reported hostname and
the scopes, so a stolen code cannot be approved blind.

### Token storage

1. `PROVISIO_TOKEN`, when set, wins and is used as is. No file is read or written, no refresh happens. This
   is the CI path.
2. The OS keychain where there is one (macOS Keychain, Windows Credential Manager, Secret Service on
   Linux), through a small Go library behind an interface in the auth module.
3. Otherwise `~/.provisio/credentials`, mode 0600 in a 0700 directory. The CLI refuses to read it if the
   permissions are looser and says how to fix them. The file holds the refresh token and the current
   access token, and is written atomically (write to a temp file, rename).

Tokens never go to git, to command output, or to logs. Every error that includes a request is redacted to
the method, path and status. `whoami --json` omits token values. A test asserts that no token string
reaches stdout, stderr or the log file in any command path.

### Refresh and expiry

- Before a network call, if the access token expires in under a minute the CLI refreshes. On a 401 it
  refreshes once and retries once. A lock file serialises concurrent refreshes, because rotating refresh
  tokens would otherwise invalidate each other when two commands run at once.
- An expired or revoked refresh token gives one clear message: `Your Provisio session has expired. Run
  provenance login.` and exit status 3, distinct from a general failure.
- `PROVISIO_TOKEN` is never refreshed; when it is rejected the message says the token was revoked or
  expired and names the variable.

### Which commands need a session

Local commands never read the credential store and never touch the network, so they keep working logged
out, offline, and in a repo with no account: `init`, `create`, `open`, `edit`, `revise`, `complete`,
`deprecate`, `repin`, `status`, `history`, `diff`, `lint`, `check`, `stale`, `next`, `govern`, `graph`,
`context`, `search`, `reconcile`, `compile`, `migrate`, `hooks`, `install-skills`, `install-plugin`,
`evidence`, `run-specs`, `add-scope`. A test runs each with an empty HOME, no network and no credential
and expects the same result as today.

| Command | Session | Behaviour |
| --- | --- | --- |
| `sync` | no, unless a shared set is Provisio-hosted | Keeps refreshing shared-repo caches from git remotes as today. Once shared sets can live on Provisio it reads them through the session, and logged out it uses the cache and says so. |
| `publish` | yes | Opt-in per project. Shows exactly which versions will become public, asks (or `--yes`), writes missing version records oldest first, then updates the head with compare-and-swap. Re-running with nothing new writes nothing. |
| `clone <handle/project or at:// URI>` | yes for private, no for public reads | Creates a local project from published records, using the files store. Public records can be read without a login. |
| `import` | yes | Brings versions that exist only on AT Proto (made in the UI, `origin: ui`) into the local git project as new versions with their reason and author. Refuses when the local record has moved past the base the UI edit was made on, and says to `revise`; it does not merge. |

When a command needs a session and there is none, it exits with status 3 and `This command needs a Provisio
session. Run provenance login (or set PROVISIO_TOKEN in CI).` It never prompts in a non-interactive shell.

### Same session model everywhere

`login` is a thin wrapper in each product CLI over the shared Go auth module and one credential file
(DESIGN, "One Provisio login for every CLI"). The UI gets the same access token as a cookie. Scion later
verifies the same token against the same JWKS. The CLI's `record.Store` Provisio backend is the only code
that talks to the record server; everything above `record.Store` is unchanged, which is what keeps local
commands independent of the network.

## 5. Records in AT Proto, and what the UI writes

Lexicons are as in DESIGN: a mutable head `dev.provisio.provenance.record` (key: the prov id), an
append-only `dev.provisio.provenance.version` (key: TID) chained to its parent by strong reference, and
`dev.provisio.project`. The slice adds two fields to the version record: `origin` (`git` or `ui`) and, for
`ui` versions, `base_version` and `base_content_hash` (what the editor started from).

**Reading.** The record server lists a user's collections with `listRecords` and gets heads with
`getRecord` on the user's own PDS, so no indexer is needed to show your own records. Cross-user views wait
for the indexer.

**Writing from the UI.** A new version, not an overwrite: compute the next version number and
`content_hash` (the server recomputes it with the TypeScript implementation and rejects a mismatch against
the conformance corpus), write the version record, then update the head with `swapRecord` on the head's
CID. If another writer moved the head, the server answers 409 with the current head and the UI shows the
conflict. This replaces the UI's pull-request flow for published records only; records edited in a git
repo keep the PR flow.

**Limits to check.** Record size limits and write rate limits on the PDS (linespec has 526 versions, up to
27 KB each, so batch `applyWrites`); permission scopes (decision and risk below).

## 6. Operations on the miren-provisio cluster

Everything below is a plan; the cluster, DNS and secrets are Caleb's and provisio-mgr's to approve.

**Apps and routes**

| App | Route | State |
| --- | --- | --- |
| `provisio-pds` | `*.provisio.social` and the PDS host (for example `pds.provisio.social`) | one fixed instance, one disk |
| `provisio-api` | `auth.provisio.dev` and `api.provisio.dev` | one instance first, SQLite on a disk |
| UI | stays on Vercel on a `provisio.dev` host | none |

Deploy order, from the proof's findings: the first deploy to a cluster with no routes becomes the default
route, so deploy a placeholder first or run `miren route unset-default` at once, and add the real routes
before the first real deploy. Raise the route idle timeout (`miren route timeout`) for the PDS host if
relays will connect, because the default is 60 seconds. A signup flow should retry the first HTTPS request
to a new handle once (certificate issuance took about 4 seconds in the proof).

**Environment and secrets** (names only; values live in `miren secret set` secrets bound with
`miren env set -e KEY --ref <path>`; a secret reference pins a version, so a rotation needs a new `env set
--ref`)

| App | Secrets | Plain environment |
| --- | --- | --- |
| `provisio-pds` | PDS admin password, JWT secret, PLC rotation key, SMTP URL, R2 access key id and secret, backup `age` recipient is public | hostname, data directory, blobstore location, PLC URL, crawler list, invite-required, R2 endpoint and bucket, backup interval |
| `provisio-api` | OAuth client private JWKS, session-signing key, cookie secret, token-hash pepper, R2 access key id and secret | public client URL, PDS hostname, allowed UI origins, DB path, backup interval, `age` recipient |

The PDS setting names are those of the reference image's environment as I remember them; confirm against
the pinned version at M7. The admin password and the rotation key are never held by an agent.

**DNS (Caleb owns it)**

- `*.provisio.social` wildcard CNAME to the cluster host (works for wildcards; the apex cannot be a CNAME,
  so the apex, if it needs to answer, uses an ALIAS or an A record to the static IP).
- `auth.provisio.dev`, `api.provisio.dev` CNAMEs to the cluster host; the UI custom domain on Vercel.
- CAA records permitting Let's Encrypt, checked before the first certificate.
- No `_atproto` TXT records are needed with the HTTP method: the proof showed the PDS answering
  `/.well-known/atproto-did` per handle hostname with the original Host header.

**Backups (in the app, to R2, as proven).** The CI binding cannot run `miren disk backup` (403) and Miren
has no scheduler, so the PDS image gets a small wrapper process that every interval takes an online SQLite
backup of each database in the data directory (`.backup` or `VACUUM INTO`, never a file copy), tars them,
encrypts to the public `age` recipient and uploads with a SigV4 PUT to R2. The `age` identity and the
rotation key have separate off-site copies in Caleb's password manager. Blobs go to an R2 blob store so
they are not on the disk at all (provenance records use almost none). The auth service uses the same
pattern for its SQLite file. Restore is local: download, decrypt, restore into a new disk and switch the
app's disk name, since a mounted disk cannot be restored over. R2 has no write-only token, so the bucket
gets a lifecycle rule and a second, separately held copy of the newest daily backup.

**The Let's Encrypt limit.** 50 new certificates per registered domain per week, and Miren issues one per
handle, so `provisio.social` signups would cap at about 50 a week (renewals are exempt). It does not bind
the first part of the slice, because Bluesky accounts need no certificate from us. It binds before any open
signup. Options:

| Option | Effect | Cost |
| --- | --- | --- |
| A. Invite-only beta capped under the limit | no change needed; matches decision 3 | a ceiling of about 50 new handles a week |
| B. Ask Miren for a wildcard certificate on the handle domain (DNS-01) | removes the limit; one certificate | depends on Miren; ask hi@miren.dev |
| C. Ask Let's Encrypt for a higher limit | raises the ceiling | their process and timing, not ours |
| D. Resolve handles by DNS TXT (`_atproto.<handle>`), created per signup through the DNS provider's API | no per-handle certificate at all | a DNS API token held by the auth service, one record per account, and the PDS must still answer for its own host |
| E. Put a DNS provider's proxy in front with its own wildcard certificate | removes the limit | bypasses Miren's `/tls-check` flow and moves DNS hosting; the least preferred |

Recommendation: A for the beta, B asked now (it costs an email), D as the fallback if B is refused. Do not
build D before B is answered.

## 8. Decisions needed from Caleb

Each has a recommendation.

1. **Handle domain.** DESIGN decided `provisio.social`. Confirm the format `name.provisio.social`, a
   reserved-name list (`admin`, `api`, `auth`, `pds`, `www`, product names), and which DNS provider holds
   the zone. Recommend: keep it; DNS at a provider with an API (it keeps option D open), DNS-only.
2. **PDS software and version.** Recommend the reference `@atproto/pds` image, pinned by digest to a
   release chosen at M7 and bumped deliberately. Other implementations exist, but this server holds users'
   signing keys and the reference one has the most review. Decide who watches its releases.
3. **Account creation flow.** Recommend invite codes only for the beta (admin-minted), created through the
   auth service with an email address for verification; the user sets their own password at the PDS, so
   Provisio never holds one. Open signup waits for the certificate option in section 6.
4. **Clerk coexistence.** Recommend a flag in the UI: both sign-ins available for a few weeks, one DID
   table with a `clerk_id` link, no data moved for Scion yet, Clerk removed from the UI at M9. Scion keeps
   Clerk until its own slice.
5. **Who administers the PDS.** Recommend Caleb holds the admin password and the rotation key (password
   manager, separate off-site copies), agents never do, provisio-mgr keeps the runbook, and a second human
   administrator is named before real users arrive.
6. **Data model: AT Proto against git.** Recommend git canonical, AT Proto the published copy, UI edits as
   `origin: ui` versions imported back by the CLI, conflicts surfaced rather than merged. The alternative
   (AT Proto canonical for UI-created projects) can come later through the `record.Store` interface
   without changing the CLI above it.
7. **Public-only first slice.** Everything on AT Proto is public, and the UI today handles private repos.
   Recommend this slice serves published records only, keeps GitHub tokens behind the flag for private
   repos, and follows with a private store in the record server's own database (not in the PDS) rather than
   waiting for AT Proto Spaces. Say yes or no to shipping the UI with that gap.

## 9. Risks

- **OAuth correctness.** AT Proto OAuth (DPoP, pushed authorization requests, client assertions, handle and
  DID resolution) is easy to get subtly wrong. Use the official client library and its test vectors; do not
  hand-roll.
- **Permission scopes.** DESIGN wants `dev.provisio.*`-only grants. Servers on older software may only
  offer broad access. If so the consent screen is broader than we want; check against the Bluesky PDS in
  M1 and decide whether to wait for granular scopes.
- **Accidental publishing.** Public by default once published. `publish` shows what will go public and
  asks first; the UI's AT Proto mode labels records as public.
- **Key custody.** The PDS holds repo signing keys and the auth service holds OAuth sessions for everyone.
  Separate off-site copies of the rotation key and the backup identity; no agent holds either; the PDS
  admin password stays out of the repo and out of #provisio.
- **Single instance, single disk, early-access cluster.** No replication; the backup is the protection.
  The restore drill in M7 must pass before real accounts, and be repeated after a cluster upgrade.
- **Certificates.** The weekly limit (section 6), plus the first-request failure during issuance.
- **Two verifiers during dual-run.** The UI and later Scion accept Clerk and Provisio sessions at once;
  each path is a way in. Keep the Clerk path read-only where possible and time-boxed.
- **Hash drift between Go and TypeScript.** The conformance corpus is the guard; M0 extends it before any
  server accepts writes.
- **Write limits.** PDS rate and record-size limits against a 526-version publish; batch writes and test
  with linespec's real data.
- **CLI credentials on shared machines.** Keychains are missing on headless Linux, so the 0600 file is the
  common path there; the mode check and `PROVISIO_TOKEN` for CI are the controls.
- **No owner for TypeScript services and the UI.** M1, M3, M5 and M8 have no worker. Without one the plan
  slips; this is the first thing for provisio-mgr to settle.
- **Federation exposure.** Once crawled, the Provisio PDS's public records appear on the open network.
  Decide at M7 whether to request crawling or stay quiet until launch.
